## How to apply — `git am` or `git apply`

All eight files are **mailbox format** (a `From`/`Subject` header, a message, a
diffstat, then the diff), so either command works. `git am` is preferred: it keeps
the commit message, and the message is where the reasoning lives.

```bash
git am /path/to/patches/admin-panel-3-salon-plans.patch    # makes a commit
git apply /path/to/patches/admin-panel-3-salon-plans.patch # leaves it uncommitted
```

If `git am` stops half-way (`Patch failed at …`), the repository is mid-rebase:

```bash
git am --abort        # back to where you were, nothing applied
git am --3way <file>  # retry, resolving against the current tree
```

`git am` needs an identity (`user.name` / `user.email`); `git apply` does not. A
plain `git diff` file cannot be fed to `git am` ("Patch format detection failed") —
that means the file is not one of these eight.

## 1. Backend — `rightserveinfotechsystems/my_naai_backend`

```bash
cd my_naai_backend

git am /path/to/patches/backend-1-shop-categories.patch
git am /path/to/patches/backend-2-booking-request-leads.patch
git am /path/to/patches/backend-3-shop-bulk-products.patch
git am /path/to/patches/backend-4-salon-plans.patch

# or `git apply` for any of them, if you would rather review before committing

# 3 adds exceljs (the xlsx template + the sheet reader). The lockfile is in the
# patch, so `npm ci` is enough; `npm install` also works.
npm ci          # or: npm install

# The schema. Idempotent — run them before restarting, on production and on staging.
psql "$DB_URL" -f migrations/2026-11-05-shop-categories-leads-bulk.sql
psql "$DB_URL" -f migrations/2026-11-05-partner-plans.sql

# The second one also carries one DATA change, deliberately not left to a boot
# side effect: it extends a still-running free trial to 90 days, so salons created
# under the old 20-day rule are not disadvantaged. It only touches the free plan
# and only while the original window is still open — a paid plan is never touched
# and an expired trial is not resurrected. Preview it first (the SELECT is in the
# file, above the UPDATE).

# Restart the process (the sweeper is an in-process cron, started from index.js).
```

If `psql` is not how you deploy, the code also repairs its own schema once per
process (`src/database/config/ensureShopSchema.js`, called at boot and lazily by
every service), so the API answers even if the migration is forgotten. **Run the
migration anyway**: it is the only thing that re-files the old free-text product
categories onto the seven real ones, and a boot-time side effect that rewrites a
catalogue is exactly what nobody wants at 2 a.m.

### What this deploys

**Categories (patch 1)**

```
POST /api/shop-categories/list            any signed-in user
POST /api/shop-public/categories/list     no token (POST + GET, 5 min cache)
POST /api/shop-categories/admin/list      admin — rows + productCount + unmatched
POST /api/shop-categories/admin/create    admin — { label, sortOrder? }
POST /api/shop-categories/admin/update    admin — { id, label?, sortOrder?, isActive? }
POST /api/shop-categories/admin/delete    admin — { id, reassignTo? }
```

`shop_products.category` now stores a category **id** and product create/update
validate it (`Unknown category "x" — use one of the ids from the category list`).
An empty value is still allowed (the shop falls back to inference). The id of a
category is fixed at creation; renaming a label never moves products.

**Booking-request leads (patch 2)**

```
POST /api/bookingRequest/salon/list       salon token — { salonId?, status?, page?, limit?, fromDate?, toDate? }
POST /api/bookingRequest/salon/summary    salon token — { salonId?, range? }
POST /api/bookingRequest/admin/list       admin token — { salonId?, status?, search?, page?, limit?, … }
POST /api/bookingRequest/admin/summary    admin token — { range?, salonId?, … }
```

Plus the 60-second answer window: `expires_at` is stamped server-side on create,
`owner-action` writes `responded_at` / `booking_id` and refuses an expired request,
and `cron/bookingRequestSweeper.cron.js` writes the auto-cancels every 20 seconds
and notifies the customer and the salon. A missed lead is never a rejection.

**Bulk upload (patch 3)**

```
GET  /api/shop-products/bulk/template?format=xlsx|csv
POST /api/shop-products/bulk/import     multipart: file, mode, dryRun
POST /api/shop-products/bulk/undo       { importId }
```

One transaction per row, dry run first, sheet row numbers in the report, and
`bulk_import_id` on every created row so an import can be undone exactly.

### Smoke checks after deploying

```bash
# categories, no token
curl -s -X POST https://backend.mynaai.in/api/shop-public/categories/list | head -c 300
# → {"status":"SUCCESS","data":{"categories":[{"id":"hair-care","label":"Hair care",…

# the template is a real xlsx
curl -s -D- -o /tmp/t.xlsx https://backend.mynaai.in/api/shop-products/bulk/template \
  -H "Authorization: Bearer $ADMIN_TOKEN" | grep -i content-disposition
# → attachment; filename="naai-shop-product-template.xlsx"

# the salon's leads (a salon token)
curl -s -X POST https://backend.mynaai.in/api/bookingRequest/salon/list \
  -H "Authorization: Bearer $SALON_TOKEN" -H 'Content-Type: application/json' \
  -d '{"status":"ALL","page":1,"limit":20}' | head -c 300
```

Then, on the website: open **Naai Shop** and check the Category select shows the
panel's labels in the panel's order.

## 3. Mobile app — `rightserveinfotechsystems/my_naai_app`

```bash
cd my_naai_app
git am /path/to/patches/app-1-salon-plans.patch
# no new dependency: AsyncStorage and axios are already in the app
```

Both subscription screens stop carrying their own prices and read
`POST /api/salons/plans/list` — the same list the website reads — so a price change
in the panel reaches the app without a release. The patch is independent of all the
others; it only needs the backend from `backend-4` deployed to have something to
read (until then it renders its seed, which matches the seeded rows).

The tab is gated like the others: the admin's `accessTab` list must include
`bookingRequests` for the tab to appear (Role Management → the role's tabs). If a
role should see it and does not, add it there — the page redirects to `/login`
when the key is missing, which is the same guard every other page uses.

### What to check, in the panel

1. **Booking Requests** → tiles show Received / Accepted / Rejected /
   **Auto-cancelled** / Answer rate; the numbers add up to Received.
2. Open a request that nobody answered: the drawer says *"No answer within 60
   seconds — the slot was released automatically"*, and it is **not** counted as
   rejected.
3. Open an accepted request: the drawer links the booking it created, and the salon
   report's Accepted column matches.
4. Salons table: sort by Missed (default, worst first); a salon that never answered
   shows **—** for median reply, not 0.
5. **Export CSV** with a filter set → the file has the filtered rows, not the page.
6. **Shop Products → Categories**: add "Nail care" → reload the website's shop →
   the new chip is there, last, with that label. Rename it → the id under it does
   not change. Hide it → the chip leaves the filter, the products keep it.
   Try to delete one with products → refused with the count; choose where to move
   them → deleted.
7. **Shop Products → Bulk add**:
   - Download the sample → it opens in Excel/Sheets with 16 headers and three
     sheets.
   - Upload it with two bad rows → the report names the **sheet row number**, the
     column and the fix; **Import N** creates only the good ones.
   - **Undo this import** removes exactly those products.
   - Upload a `.pdf` → refused with "upload an .xlsx or .csv file".
   - Upload the same sheet twice with "Skip them" → the second run reports
     SKIPPED, not FAILED, and the catalogue count does not move.
8. The product editor's **Category** select now lists the same categories; a
   product that still holds an old free-text shelf shows it as *"(not in the
   list)"* rather than a blank field.

## Rollback

The patches are additive: no endpoint changes shape, no table is dropped and no
existing column changes meaning. To undo an application:

```bash
git apply -R <patch>        # in the reverse order you applied them
git reset --hard <commit>   # or, if you applied them with `git am`
```

Applying with `git am` makes one commit per patch, so the clean way back is
`git reset --hard` to the commit you were on before (or `git revert` for the ones
you want to keep in history).

The three database changes that alter existing rows are in the migrations, not the
code, and each is recorded there so it can be reversed deliberately:

- the legacy free-text category → category id re-file (a `SELECT` is printed above
  it in the file to review what it will touch);
- the backfill of `expires_at` for rows created before this release, and the
  auto-cancel of any still-PENDING row past its window;
- `partner-plans.sql` extends a **still-running** free trial to 90 days. To undo
  it: `UPDATE salons SET plan_end_date = plan_start_date + INTERVAL '20 days' WHERE
  plan_type IN ('FREE','Free') AND plan_end_date > NOW();` — but read the reasoning
  in the file first; the salons affected were being told 20 days and are now told
  90, which is the change the client asked for.

Everything else (`shop_categories`, `shop_product_imports`, the four optional
product columns, the four `booking_requests` columns) is new and can simply stay.
